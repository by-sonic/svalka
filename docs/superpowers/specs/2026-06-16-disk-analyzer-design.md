# Анализ диска (Disk Analyzer) — дизайн

- **Дата:** 2026-06-16
- **Статус:** утверждён к реализации
- **Проект:** Svalka
- **Автор:** brainstorming-сессия (Sonic + Claude)

---

## 1. Проблема и зачем

Svalka умеет чистить *известный* мусор по фиксированным путям (temp, кэши
браузеров, dev-кэши и т.п.). Но самый частый вопрос пользователя — **«куда
вообще делось место на диске?»** — она не отвечает. Большие личные файлы
(ISO-образы, видео, дампы, забытые архивы), раздувшиеся папки приложений,
неожиданные гиганты — всё это вне списка категорий.

Добавляем пятый экран — **«Анализ диска»**: treemap использования диска с
drill-down по папкам и список самых крупных файлов. Удаление выбранного идёт
через **тот же карантин** (обратимо), а защищённые системные файлы физически
нельзя выбрать (deny-list). Фича укладывается на существующий движок: один
новый модуль ядра, одна IPC-команда, один Svelte-экран; удаление —
переиспользование готового `quarantine_items`.

## 2. Scope

**В v1:**
- Treemap использования выбранного диска/папки, плитки по площади ≈ байтам.
- Drill-down: клик по папке — внутрь; хлебные крошки — наружу.
- Список «самых крупных файлов» (топ-N) в текущей области.
- Перенос выбранного в карантин (обратимо), с учётом deny-list.
- Заголовок: занято/свободно/всего по диску.

**Отложено (отдельный спек, не сейчас):**
- **Поиск дублей** — другой и тяжёлый алгоритм (хеширование содержимого, а не
  измерение размера). Пихать в v1 — раздуть scope.
- Squarified treemap (правильная раскладка квадратами). v1 — простые
  пропорциональные плитки в строках (slice-and-dice).
- Кэш результатов обхода между drill-down (см. §7, известная стоимость).
- Выбор произвольной папки через системный диалог — v1 стартует с диска из
  списка, дальше drill-down покрывает любые подпапки.

**Non-goals:** не дефрагментируем, не «оптимизируем» реестр, не трогаем
ничего необратимо. Анализатор только показывает и (по явному выбору) кладёт в
карантин.

## 3. Экран и поведение (UX)

Раскладка (см. утверждённый макет `svalka_disk_analyzer_screen`):

1. **Шапка:** селектор диска (список существующих логических дисков) + полоса
   «занято N из M ГБ · свободно K» + кнопка `Сканировать`.
2. **Хлебные крошки:** `C:\ › Users › Sonic`. Клик по сегменту — подъём на этот
   уровень.
3. **Treemap:** плитки текущего уровня, отсортированы по убыванию размера,
   ширина ≈ доля в размере уровня. Папки кликабельны (drill-down). Защищённые
   системные узлы (`hiberfil.sys`, `pagefile.sys`, `\Windows\System32`, …)
   отрисованы пунктиром с замком и **не выбираются**.
4. **Самые крупные файлы:** топ-N отдельных файлов в текущей области, с размером
   (моно) и кнопкой `в карантин`. Защищённые помечены и не выбираются.
5. **Подвал:** «выбрано K · X ГБ» + акцентная кнопка `В карантин · обратимо`.

**Состояния экрана:** `idle` (до первого скана) → `scanning` (индикатор +
прогресс по верхним папкам) → `result` → `empty` (пусто/0 байт) → `error`
(сообщение, как в остальных экранах — без «молчаливых» провалов).

**Поток выбора → карантина:** пользователь отмечает плитки-файлы и/или строки
крупных файлов → `В карантин` → вызывается `quarantine_items` → тост с
освобождённым объёмом и числом пропущенных (занятые/недоступные) → область
перерисовывается (повторный `analyze_disk` текущего узла).

## 4. Архитектура и поток данных

```
UI (Usage.svelte)
  └─ api.analyzeDisk(root)  ──▶  command analyze_disk (spawn_blocking)
                                   └─ svalka_core::usage::analyze(root)
                                        ├─ параллельный обход (по верхним детям)
                                        ├─ дерево размеров (bounded)  ─┐
                                        └─ топ-N крупных файлов  ──────┤
  ◀── UsageReport { total, free, volume_total, tree, largest } ◀─────┘
  └─ выбор → api.quarantineItems("Анализ диска", volumeRoot, paths)
                                   └─ существующий quarantine_items (без изменений)
```

Ключевой принцип: **новой логики удаления нет.** Анализатор лишь находит пути;
удаление — это уже отлаженный обратимый `QuarantineStore::quarantine_paths`.

## 5. Ядро — `crates/svalka-core/src/usage.rs` (новый модуль)

### 5.1 Модель

```rust
pub struct UsageNode {
    pub name: String,      // basename для отображения
    pub path: PathBuf,
    pub size: u64,         // суммарный размер поддерева (для папок — рекурсивно)
    pub is_dir: bool,
    pub protected: bool,   // !scanner::is_allowed(path) → нельзя в карантин
    pub children: Vec<UsageNode>, // заполнены до предела глубины/ширины
}

pub struct LargeFile {
    pub path: PathBuf,
    pub size: u64,
    pub protected: bool,
}

pub struct UsageReport {
    pub root: PathBuf,
    pub total: u64,            // суммарный размер под root
    pub free: u64,             // свободно на томе (Win32)
    pub volume_total: u64,     // ёмкость тома (Win32)
    pub tree: UsageNode,       // root с детьми (ограничено)
    pub largest: Vec<LargeFile>, // топ-N файлов под root, по убыванию
}
```

Все поля `#[derive(Serialize)]` (как `model::CleanItem`), `PathBuf`
сериализуется в строку, потребляется фронтом.

### 5.2 Алгоритм

`pub fn analyze(root: &Path, limits: Limits) -> UsageReport`

- `limits` = `{ depth: u8 = 3, top_children: usize = 16, top_files: usize = 100 }`
  (значения — константы по умолчанию, заданы рядом с модулем).
- Читаем непосредственных детей `root`. **Каждого ребёнка обходим параллельно**
  (rayon, по верхним детям — там и сосредоточен объём), чтобы скан большого
  диска не тянулся последовательно.
- Для каждого ребёнка `scan_node` рекурсивно:
  - файл → вклад в размер + предложить в bounded-heap топ-файлов; узел-лист;
  - папка → суммируем размеры детей; **дети сохраняются в дерево только пока
    `depth < limits.depth`**, глубже — узел знает свой размер, но `children`
    пуст (полезная нагрузка ограничена). Дети сортируются по убыванию; всё за
    пределами `top_children` сворачивается в синтетический узел
    `«остальное (N элементов)»` с суммарным размером.
  - `protected = !scanner::is_allowed(path)`.
- **Reparse points (junction/symlink) не раскрываются** — берутся как лист
  (как в `quarantine_tree`), чтобы исключить циклы и двойной счёт
  (`C:\Users\All Users` и т.п.).
- Нечитаемые/исчезнувшие пути дают вклад 0 и **никогда не паникуют** (как
  `sizer::dir_size`).
- Топ-N файлов: per-child bounded min-heap (размер N), затем слияние в
  глобальный — без общего мьютекса под нагрузкой.
- `free` / `volume_total`: Win32 `GetDiskFreeSpaceExW` по корню тома
  (gated `#[cfg(windows)]`; на не-Windows возвращаем 0/0 — ядро остаётся
  кросс-компилируемым и тестируемым).

Drill-down глубже предела (§3) фронт делает **повторным вызовом
`analyze_disk(subpath)`** — та же функция с другим `root`, второго механизма нет.

## 6. App — `crates/svalka-app/src/commands.rs`

Новая команда по образцу `scan` (всё тяжёлое — в `spawn_blocking`, иначе UI
зависнет, как было с «Программами»):

```rust
#[tauri::command]
pub async fn analyze_disk(window: tauri::Window, root: PathBuf) -> Result<UsageReport, String>
```

- Выполняет `usage::analyze` на блокирующем потоке.
- Прогресс: после каждого обработанного **верхнего** ребёнка эмитит
  `analyze://progress { name, size }` — полоса в шапке наполняется по папкам.
- Возвращает `UsageReport` (или строку-ошибку — surface в UI, без проглатывания).

Опционально: `list_drives() -> Vec<String>` — существующие корни логических
дисков (перебор `A:`..`Z:`, `Path::exists`), для дропдауна. Без новых
зависимостей.

**Удаление переиспользует существующий `quarantine_items`** один в один:
`source = "Анализ диска"`, `volume_root` = корень тома выбранных путей
(на экране сканируется один диск, значит все выбранные пути — на одном томе →
один вызов). Защита: фронт не даёт выбрать `protected`, и перед вызовом
повторно отсеивает `protected`-пути (defense-in-depth).

## 7. UI — `ui/src/routes/Usage.svelte` (новый) + правки

**Роутинг** (`ui/src/App.svelte`): добавить `"usage"` в union `Tab`, пункт в
массив `nav` (label «Анализ диска», icon `analyze`), ветку в `{#if}`-цепочку
(4 → 5 экранов).

**Иконка** (`ui/src/lib/Icon.svelte`): добавить именованную иконку `analyze`
(treemap/диаграмма) — сейчас иконки плейсхолдерные, добавляем в общий набор.

**IPC** (`ui/src/ipc.ts`): типы `UsageNode` / `LargeFile` / `UsageReport`;
`analyzeDisk: (root) => invoke<UsageReport>("analyze_disk", { root })`;
`listDrives: () => invoke<string[]>("list_drives")`. Удаление переиспользует
существующий `api.quarantineItems`.

**Компонент `Usage.svelte`:**
- Локальное состояние: `report`, `crumbs: string[]` (стек путей для drill-down),
  `selected: Set<string>`, статус (`idle`/`scanning`/`result`/`error`).
- Treemap — простые пропорциональные плитки (CSS flex `flex-grow` ≈ размеру, в
  1–2 строки), как на макете. Без canvas и сторонних либ.
- Подписка на `analyze://progress` (как `scan://progress` в `Clean.svelte`),
  снятие листенера при размонтировании.
- Переиспользует классы из `app.css` (`listrow`, `chip`, `btn`, `progress`,
  `spinner`, `skel`, `empty`) и хелперы `lib/format.ts` (размеры/числа).

**Известная стоимость:** drill-down за предел глубины перескан подпапки заново
(кэша нет — отложено в §2). Подпапка меньше родителя, так что стоимость падает
с глубиной; полный обход диска случается один раз на верхнем уровне.

## 8. Обработка ошибок и edge-cases

- Несуществующий/пустой `root` → `UsageReport` с `total = 0`, пустым деревом
  (как `sizer`). UI показывает `empty`.
- Нет прав на папку → пропуск, вклад 0, без паники. (Опционально: счётчик
  пропущенных для подвала — необязательно в v1.)
- Junction/symlink → лист, без рекурсии (анти-цикл).
- Защищённые пути (`is_allowed == false`) → `protected = true`, невыбираемы;
  плюс повторный отсев перед карантином.
- Огромное дерево → полезная нагрузка ограничена `depth`+`top_children`+
  «остальное» (сотни узлов максимум).
- Карантин занятого/недоступного файла → уже покрыто `quarantine_items`
  (пропуск с причиной, не фатально).
- Восстановление поверх занятого пути → уже покрыто `restore` (отказ без
  перезаписи).

## 9. Безопасность

- **Deny-list (`scanner::is_allowed`)** — единый источник правды о
  защищённости; анализатор только переносит флаг в UI и отсеивает перед
  карантином. System32/WinSxS/`hiberfil.sys`/`pagefile.sys`/cookies и т.п. не
  выбираются.
- **Обратимость** — удаление = перенос в карантин (атомарный move на том же
  томе), не `delete`. Полностью отыгрывается через существующий `restore`.
- **Нет новой логики удаления** — переиспользуется проверенный
  `quarantine_paths` со всеми его инвариантами (атомарный манифест, откат при
  сбое записи, изоляция по нумерованным подпапкам).

## 10. Тестирование

Юнит-тесты ядра в `usage.rs` (стиль существующих, `tempfile::tempdir`):

1. `analyze` суммирует `total` = сумма всех файлов поддерева.
2. Дети папки имеют рекурсивный размер и отсортированы по убыванию.
3. `largest` возвращает топ-N файлов по убыванию, не больше N.
4. Предел глубины: узлы за пределом имеют верный `size`, но пустой `children`.
5. `top_children` + «остальное»: при > K детей хвост свёрнут в один узел,
   чей размер = сумме хвоста.
6. `protected`: путь, попадающий под deny-list (например `…\Cookies`), даёт
   `protected = true`.
7. Reparse point (если создаётся на платформе) не раскрывается; иначе —
   тест-хелпер на «лист».
8. Несуществующий путь → `total = 0`, без паники.

Команды app тонкие — логика покрыта ядром (как в проекте сейчас). Win32-функция
свободного места — за `#[cfg(windows)]`, проверяется вручную/в интеграции.
`cargo clippy -p svalka-core --all-targets -- -D warnings` должен оставаться
зелёным.
